# 星海统一索引迁移与代码上线说明

建表与历史回填已由使用者执行并验证，前后端现已接入统一索引。本文说明后续切换与核对方式；代码开发和测试期间没有执行生产数据库变更。

## 已确认的归档规则

| 内容 | 业务来源 | 星海日期 | 索引条数 |
| --- | --- | --- | --- |
| 记忆 | `fm_memory` | `memory_date`，事情发生日期 | 每条记忆一条 |
| 珍藏 | `fm_time_capsule` | `DATE(created_at)`，封存日期 | 每份珍藏一条 |

珍藏的 `open_date`、`opened_at` 不进入星海索引，不再建立“封存 / 开启”两个节点。
两种来源的同一个数字 ID 不冲突，由 `source_type + source_id` 唯一区分。
同一天的多条内容保留各自的索引，统计时合并为一个日期节点，并分别计数记忆和珍藏。

日期只存一个 `DATE` 字段，不存冗余的年月日。日期发布后固定，标题由各自业务同步更新。
正文、媒体和珍藏开启状态仍保留在业务表；星海入口不能绕过详情接口的家庭权限及开启限制。

## 文件与执行顺序

1. `20261020_01_universe_index_schema.sql`：新增 `fm_universe_index` 和索引。
2. `20261020_02_universe_index_backfill.sql`：先运行开头的检查查询；结果为空后，再执行事务部分。
3. `20261020_03_universe_index_verify.sql`：核对分类数量、缺失、字段差异及多余索引，最后查看按天计数。

脚本按仓库现有 MySQL 8.0 表结构编写，目标库名为 `family_memory_new`，执行前核对该库名。
不要为这次迁移运行 `database/schema.sql`：现有初始化脚本包含删除业务表的语句。

建表属于 DDL，会自动提交，不能与历史回填视为一个可统一回滚的事务。
回填使用单独事务；执行客户端需要遇错停止，发生错误时回滚，不能继续提交。

## 历史回填范围

- 只导入未删除家庭内、未删除的记忆和珍藏。
- 保留原业务日期和标题，不用当前日期替代历史日期。
- 只写新索引表，不移动或修改原记录，不调用珍藏详情接口，也不会触发珍藏开启。
- 唯一键防止重复插入；重复回填会按原业务数据修正索引的家庭、日期、标题及有效状态。
- 重跑时会逻辑删除业务已不存在、已删除或家庭已失效的旧索引，不硬删除索引历史行。

新代码已在记忆、珍藏的发布、标题修改和删除事务内维护索引。如果回填之后旧版后端又接受了业务写入，
切换前需暂时停止这些写入，重跑幂等回填和核对脚本，再启动新后端，确认后恢复写入。
新代码运行后，日常同步由各业务事务完成，不需要每次启动重新回填。

## 已实现的前后端读取方式

- 记忆、珍藏发布：业务数据与索引同事务写入。
- 标题修改：对应业务在同一事务中更新索引标题；不修改归档日期。
- 删除内容：业务逻辑删除与索引逻辑删除同事务执行。
- 初次进入星海：只返回有数据日期的记忆数量、珍藏数量，服务端组织年月日层级。
- 概要完成后：后台按年份游标分批读取索引 ID、来源类型、来源 ID、归档日期和标题，优先浏览中的年份。
- 点击日期：从当前星海会话的内存缓存聚焦展开，不再按点击读取日期列表。
- 点击内容：调用原记忆或珍藏详情接口。
- 搜索：按当前家庭查询索引标题，返回匹配项及日期路径；不复制或搜索封存正文。
- 前端：背景先显示，概要节点按层级分帧加入；年份索引后台自动加载、逐批补入星点，刷新页面重新请求，不使用版本号或持久化索引缓存。

## 全项目中文注释

`../update.sql` 覆盖实际数据库的14张表、123个字段，包含枚举取值与逻辑外键来源。
它仅更新表及字段注释，保留生成时读取的字段定义；未自动执行。不要将它与初始化脚本混用。
全部后端主代码的类、显式字段、方法、参数以及旧Map响应字段均已补充中文说明。
接口契约与加载流程见 `../../docs/星海统一索引与异步加载.md`。

日期范围查询使用 `node_date >= 起始日期 AND node_date < 下一段起始日期`，
不要在范围筛选条件中对日期列包裹 `YEAR()` / `MONTH()`，以便利用家庭日期索引。
任何服务端查询都必须先验证家庭成员权限，再限定 `family_id` 与 `deleted = 0`。
